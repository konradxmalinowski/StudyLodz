# English language toggle for the marketing website

## Scope
`website/index.html` and `website/privacy.html` only. The mobile app stays Polish-only
(deliberate, per CLAUDE.md). No new URLs — a single page per language, switched client-side.

## Mechanism
- New `website/i18n.js`: a `TRANSLATIONS = { pl: {...}, en: {...} }` dictionary plus
  `applyLanguage(lang)` that walks every `[data-i18n]` element and sets its content, updates
  `<title>`/meta description/OG/Twitter tags, sets `<html lang>`, and updates the toggle
  button's label to the *other* language.
- Every translatable HTML element gets `data-i18n="key"`. `<body data-page="index|privacy">`
  tells the script which page-specific meta keys to apply.
- Preference persisted in `localStorage` under `site_lang`; defaults to `pl` if unset.
- Toggle is a small pill button in the header nav (`.lang-toggle`), not a link — no page
  navigation, no URL change.
- Script is external (`<script src="i18n.js" defer>`), so the existing
  `default-src 'self'` CSP covers it with no changes needed (script-src falls back to
  default-src, and 'self' permits same-origin external files without 'unsafe-inline').

## Privacy policy accuracy
Since this adds a new `localStorage` write (site language preference, separate from the
app's `APP_COLOR_SCHEME_OVERRIDE` theme key), `privacy.html`'s "data stored locally" section
gets one added sentence disclosing the `site_lang` key — keeps the policy accurate.

## Verification (the user's explicit ask: check every element really has a translation)
A throwaway Node script scans both HTML files for every `data-i18n="..."` key actually used,
then checks `i18n.js`'s `pl` and `en` dictionaries both contain a non-empty value for each —
flags any missing key in either language before this ships. Run after authoring the dictionary,
fix anything it flags, re-run until clean.

## Manual checks
- Load `index.html` and `privacy.html` locally, toggle PL → EN → PL on both, confirm every
  visible string changes and nothing is left in the wrong language.
- `html-validate` on both files (existing `website/.htmlvalidate.json` config).
- Confirm the CI `deploy-landing.yml` anchor-check step still passes (`#funkcje` etc. anchors
  unaffected by this change).

## Not in scope
- Separate `/en/` URLs, hreflang tags, or sitemap changes (single-URL toggle, not applicable).
- Mobile app i18n (out of scope per user's explicit answer to the scope question).
